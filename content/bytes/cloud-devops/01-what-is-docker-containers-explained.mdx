## The 60-second explanation

Docker helps you package an application with the files, libraries and runtime configuration it needs. That package can be started consistently on a developer laptop, test server or cloud container platform.

A **Docker image** is the packaged, read-only blueprint. A **container** is a running instance created from that image. If an image is the class, a container is an object created from it; if an image is a cake mould, each container is one cake produced from the mould.

Docker reduces environment differences, but it does not magically remove them. CPU architecture, operating-system kernel features, external services, secrets and configuration can still differ. The real benefit is that the application runtime becomes explicit and repeatable.

## Why “works on my machine” happens

Suppose a Python application runs on a developer’s laptop but fails on a server. The laptop may have Python 3.12 while the server has 3.9. A package may have been installed manually. An environment variable may exist only in the developer’s shell. The application code is the same, but its **runtime environment** is not.

Docker moves important runtime decisions into version-controlled instructions:

1. Choose a base image containing the runtime.
2. Copy dependency definitions.
3. Install dependencies.
4. Copy the application.
5. declare the command that starts it.

The resulting image carries that filesystem and configuration between environments.

## How the four Docker objects work together

<DockerObjectArchitecture />

Imagine that you have built a Python course-catalog API. These Docker objects do different jobs at different moments:

1. **The Dockerfile is an input to the build.** It records decisions such as the Python version, dependency installation and startup command. A Dockerfile does not contain your running application.
2. **`docker build` produces an image.** The image is an immutable, layered package. Give it a meaningful name and tag such as `course-api:1.0` so you know exactly which build you are testing.
3. **A registry distributes the image.** `docker push` uploads the tagged image; another machine can use `docker pull` to retrieve it. Docker Hub is one registry, but teams can use private registries too.
4. **`docker run` creates a container from the image.** The container is the live process boundary. Runtime settings—ports, environment variables, volumes and resource limits—are attached when it is created or started.

The order is important: **source code + Dockerfile → image → registry or container**. A registry never stores the running process, and a Dockerfile is not the deployable artifact. The image is the artefact that moves between environments.

### Trace one change without memorising definitions

Suppose you change the API response from `v1` to `v2`:

- The existing container does not change automatically.
- You rebuild the image and give the new build a new tag.
- You stop or replace the old container.
- You start a new container from the new image.

This is why production systems treat containers as **replaceable**. They deploy a known image rather than manually editing a running server.

## Real-time analogy: a standard shipping container

<Scenario title="The package should not depend on the vehicle">

Before standard shipping containers, goods required different handling for ships, trains and trucks. A standard container created a stable boundary: transport systems handle the container without needing to understand every item inside.

A Docker container creates a similar software boundary. The host needs a compatible container runtime; the application arrives with its expected userspace files and dependencies. The analogy has limits: Docker containers share the host kernel, while physical shipping containers do not share machinery with the ship.

</Scenario>

## Containers and virtual machines are not the same

A virtual machine normally packages a complete guest operating system and runs it through a hypervisor. A container packages application processes and userspace dependencies while sharing the host kernel. This usually makes containers faster to start and less resource-heavy than full virtual machines.

The choice is not “Docker or virtual machines forever.” Cloud systems often run containers **inside** virtual machines. VMs provide infrastructure isolation; containers provide a consistent application delivery unit.

## The smallest useful workflow

```text
application code
      ↓ docker build
Docker image
      ↓ docker run
running container
      ↓ publish a port
user reaches the application
```

Three commands reveal the model:

```bash
docker build -t my-app:1.0 .
docker run --name my-app my-app:1.0
docker ps
```

`docker build` produces an image. `docker run` creates and starts a container. `docker ps` shows running containers. The name and tag make the artifact easier to identify; they do not change its contents.

### What Docker is doing behind the command

The `docker` command is the client. It sends a request to the Docker daemon, which builds images, creates networks and volumes, and starts containers. When an image is not available locally, the daemon can pull it from a registry before creating the container.

<OfficialDockerDiagram />

Read the official diagram from left to right:

1. You enter `docker build`, `docker pull` or `docker run` through the Docker client.
2. The Docker daemon performs the requested work.
3. The daemon exchanges images with a registry when required.
4. The daemon stores images locally and creates running containers from them.

## When Docker helps—and when it does not

Docker is useful when you need consistent development environments, repeatable CI builds, service isolation, portable deployment artifacts or multiple services with different dependencies.

It may add unnecessary complexity for a small static website, a one-off local script or a platform that already hides packaging completely. Docker also does not replace application security, monitoring, backups, orchestration or cloud architecture.

## Common mistakes

<Mistakes>

- Saying an image is “running”; containers run, images are used to create them.
- Treating a container as a permanent server and storing important data only inside it.
- Assuming a container includes its own kernel like a virtual machine.
- Using the mutable `latest` tag as proof of a specific version.
- Believing containerization automatically makes an insecure application secure.

</Mistakes>

## Interview bit

<ThemeCard title="What is the difference between a Docker image and a container?" badge="CAREER">

**Strong answer:** A Docker image is an immutable, layered package containing an application’s filesystem and startup metadata. A container is a runnable instance of that image with its own process and writable layer. I can create multiple containers from one image, and I keep durable data in volumes or external services rather than relying on a container’s writable layer.

</ThemeCard>

## Key takeaways

<Takeaways>

- A Dockerfile is the recipe, an image is the package and a container is the running instance.
- Containers share the host kernel; they are not lightweight virtual machines in every technical sense.
- Docker makes runtime assumptions explicit and repeatable.
- Images should be reproducible and containers should be replaceable.
- External configuration and durable data still need deliberate design.

</Takeaways>
