## Prototype, pilot and thin production slice

A prototype answers, **Can the idea work?** A pilot asks, **Does it help a limited group?** A thin production slice asks a harder question: **Can one narrow but complete workflow create value under real operational constraints?**

The slice is thin in scope, not quality. It uses real identity, permitted data, observable execution, failure handling and an owner. It avoids supporting every user, exception and integration on day one.

## The end-to-end architecture test

A useful slice crosses the whole value path:

1. A real trigger enters through an approved channel.
2. Identity and permissions are enforced.
3. Required context is retrieved from governed sources.
4. Deterministic logic and model reasoning are separated.
5. The output is evaluated or routed for approval.
6. The action and evidence are recorded.
7. Users can correct, escalate or recover.

If a demo skips identity, source ownership, monitoring and recovery, it has not yet tested deployment risk.

## Simple analogy: test a working kitchen station

A restaurant tests one complete station—from order to prepared dish—before redesigning the whole kitchen. A thin production slice similarly tests one complete user outcome with real data, permissions and operational limits.

## Real-time scenario: equipment-maintenance assistant

<Scenario title="One equipment family, one site, one decision">

A manufacturer wants an assistant for every technician and machine. The thin slice starts with one equipment family at one plant. It retrieves approved manuals and recent service history, proposes likely checks and cites the evidence. It cannot change machine settings or close a work order. The technician chooses the action and records whether the suggestion helped.

This narrow scope tests retrieval quality, terminology, response time, permissions, user trust and feedback capture. Expansion happens only after evidence shows the system improves diagnosis without increasing unsafe actions.

</Scenario>

## Where AI belongs—and where it does not

| Need | Prefer |
|---|---|
| Exact eligibility rule | Deterministic code or rules engine |
| Search across approved knowledge | Retrieval plus citations |
| Summarise unstructured evidence | Model with evaluation and review |
| High-impact irreversible action | Explicit human approval |
| Repetitive API orchestration | Workflow engine with bounded model decisions |

AI is one component in a production system. An FDE earns trust by making model boundaries visible instead of presenting the model as the entire architecture.

## Define the production contract

Before implementation, agree on:

- Included users, cases, data and actions.
- Excluded cases and visible escalation behaviour.
- Quality threshold and representative evaluation set.
- Latency, availability and cost budgets.
- Logging, privacy, retention and access rules.
- Human approval points and action permissions.
- Rollback trigger, owner and recovery method.

## Common mistakes

<Mistakes>

- Making the scope small by using fake data and bypassing real integrations.
- Giving the model authority that deterministic policy should control.
- Measuring average model quality while hiding critical failure cases.
- Expanding to more users before learning from the first workflow.
- Treating rollback as “turn it off” without restoring the previous process.

</Mistakes>

## Interview bit

<ThemeCard title="How would you take an AI proof of concept into production?" badge="CAREER">

**Strong answer:** I would choose one valuable end-to-end workflow and define its users, data, permissions, quality threshold, operational budgets and escalation path. I would separate deterministic rules from model judgement, build an evaluation set from representative cases, instrument the workflow and deploy behind a limited rollout. Expansion would depend on outcome, risk and adoption evidence—not demo quality.

</ThemeCard>

## Key takeaways

<Takeaways>

- Thin scope does not mean weak production discipline.
- Test the complete value path with real constraints.
- Keep deterministic policy outside probabilistic model behaviour.
- Define evaluation, approval and rollback before launch.
- Expand only when evidence supports the next step.

</Takeaways>
