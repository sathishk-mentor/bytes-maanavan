## The 60-second answer

ChatGPT and Gemini do not search a hidden page containing the complete answer. A language model receives your prompt, represents it as **tokens**, processes relationships within the available context and calculates probabilities for what token could come next. It selects a token, adds it to the sequence and repeats the process until it reaches a stopping condition.

The application surrounding the model may also add system instructions, retrieved documents, conversation history, tool results and safety checks. Therefore, the answer you see is produced by a complete system—not only by the model.

## Do AI models really “think”?

“Thinking” is convenient product language, but it can create the wrong mental model. A person connects experience, intention, values and understanding. A language model performs learned mathematical operations over token representations.

Some modern systems spend extra computation on difficult problems, use tools or verify intermediate work. That can improve results, but it does not justify assuming that the model understands, believes or intends things in the human sense.

## Complete prompt-to-answer workflow

### Step 1: The application prepares the input

Your visible prompt may be only one part of the actual input. The application can combine:

- system instructions defining behaviour and boundaries;
- your current question;
- relevant conversation history;
- retrieved company documents or search results;
- outputs returned by tools;
- required response format and safety rules.

This combined input must fit within the model’s **context window**. A larger context window allows more tokens, but more context is not automatically better. Irrelevant or conflicting material can reduce response quality.

### Step 2: Text becomes tokens

A tokenizer divides text into units called tokens and maps them to numeric IDs. A token may be a whole short word, part of a word, punctuation or another text fragment. Token boundaries depend on the tokenizer; they are not the same as words.

This matters because model input limits and API usage are commonly measured in tokens. The same sentence can require different token counts across models or languages.

### Step 3: Tokens become contextual representations

The model converts token IDs into learned numerical representations. Transformer layers use **attention** to calculate which parts of the available sequence are relevant to other parts.

For example, in “The server failed because **it** ran out of memory,” attention can help the representation of “it” use information associated with “server.” This is a simplified illustration—not a claim that one attention connection fully explains the model’s final answer.

The Transformer architecture was introduced in the 2017 paper *Attention Is All You Need*. Modern products may use different transformer variants and additional system components, so a generic transformer diagram should not be presented as the exact internal architecture of ChatGPT or Gemini.

### Step 4: The model scores possible next tokens

After processing the current sequence, the model produces scores that can be converted into a probability distribution over possible next tokens.

If the current text is “The capital of Tamil Nadu is”, a highly likely continuation is “Chennai”. For an open-ended story, many continuations may be reasonable. The model is estimating a suitable continuation; it is not checking every generated statement against reality by default.

### Step 5: A token is selected

The system selects one possible next token. Configuration can influence this choice:

- **Lower randomness** generally favours more likely and repeatable wording.
- **Higher randomness** may create more varied output but can also increase inconsistency.
- **Maximum output length** limits how long generation can continue.
- **Stop conditions** tell the system when a response should end.

Exact controls differ by model and product. A user interface may not expose the same settings as an API.

### Step 6: Generation repeats

The selected token becomes part of the context for the next step. The model calculates again, selects again and continues. Streaming interfaces display pieces of the response while this loop is running, which is why text often appears gradually.

## A real-life analogy—and its limitation

<Scenario title="The sentence-completion game">

Imagine a language teacher writes, “After heavy rain, the road became…” and asks learners to complete it. They may suggest “flooded,” “slippery” or “difficult to cross.” Each choice depends on the words already present and patterns learned from earlier language experience.

An LLM performs a far larger mathematical version of sequence completion. However, the analogy has an important limit: the model does not choose from only a few visible words, and its internal processing involves many layers of learned numerical transformations.

</Scenario>

The underlying concept does not change, but the audience and constraints change the continuation the model tries to produce. This is why prompt context matters.

## Why can a confident answer be wrong?

The generation objective rewards a plausible continuation, not guaranteed factual truth. Errors can occur when:

- the prompt is ambiguous or missing essential context;
- the requested fact is newer than the available knowledge;
- supplied context is incorrect, conflicting or difficult to retrieve;
- the task requires exact calculation or specialised evidence;
- the model follows a familiar linguistic pattern that does not match reality.

Connecting an application to trusted retrieval, tools or validators can reduce particular errors, but it cannot make every answer automatically correct.

## Chat application vs language model

<ThemeCard title="Do not confuse the product with the model" badge="System view">

A **language model** generates or scores token sequences. A **chat application** can manage user accounts, conversation storage, attachments, web search, code execution, tool calls, safety policies, citations and the interface.

When two products use capable models but produce different answers, the reason may include different instructions, context preparation, tools, model versions, decoding settings or safety policies.

</ThemeCard>

## Real workplace scenario

A support team asks an AI assistant to draft a response using an approved troubleshooting guide.

1. The system receives the customer’s question.
2. Retrieval finds relevant passages from the current guide.
3. The application adds those passages and response rules to the model context.
4. The model generates a draft token by token.
5. A validator checks required fields and prohibited claims.
6. A support agent verifies the technical steps and sends or edits the response.

The model generates the language, but retrieval supplies current organisational knowledge and the support agent owns the final communication.

## Common misconceptions

<Mistakes>

- **“The model stores every training document like a database.”** Training changes model parameters; it is not equivalent to saving searchable copies of every source.
- **“One token equals one word.”** Tokens can be whole words, word fragments or punctuation, depending on the tokenizer.
- **“Attention tells us exactly why the model answered.”** Attention is an important computation, but a simple attention visual is not a complete causal explanation.
- **“Low randomness guarantees accuracy.”** It can make output more repeatable; it does not verify facts.
- **“A larger context window means the model remembers everything forever.”** Context is limited to the current request/session design and does not automatically create durable memory.

</Mistakes>

## Interview bit

<ThemeCard title="How does an LLM generate a response?" badge="Career">

**30-second answer:**

An LLM tokenizes the input, processes the token sequence through transformer layers and produces a probability distribution for the next token. A decoding strategy selects a token, appends it to the sequence and repeats until a stop condition is reached. The surrounding application may add context, retrieval, tools, safety checks and validation.

**Strong follow-up:**

Next-token prediction can produce fluent and useful language because the model learned rich statistical relationships during training. It can also produce plausible errors because generation itself does not guarantee grounding in current facts. For important use cases, I would add trusted retrieval or tools, structured validation, evaluation and risk-based human review.

## Key takeaways

<Takeaways>

- A chat product and its underlying language model are not the same thing.
- Text is represented as tokens before model processing.
- Transformer attention helps tokens use information from the available sequence.
- The model repeatedly selects a possible next token until generation stops.
- Product configuration influences variation, length and stopping behaviour.
- Plausible generation is not automatic factual verification.
- Retrieval, tools, validation and human review make production workflows more dependable.

</Takeaways>
