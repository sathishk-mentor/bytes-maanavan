## Start from Basics

Start with the smallest possible picture. Your Python code sends a message to a model provider. The provider runs an LLM and sends a reply back. For one experiment, the provider's own SDK may be all you need.

The difficulty begins when the experiment becomes an application. You now need to keep system instructions separate from user text, switch models without rewriting every call, require a predictable response shape, attach documents, expose safe tools and understand why a request failed. **LangChain is an open-source framework that gives these recurring application jobs common interfaces.**

This is the key beginner rule: **LangChain does not replace Python, your model provider or the LLM.** It organises how your Python application works with them.

Think of the model as an engine. LangChain is not another engine; it is part of the vehicle around the engine—the controls, wiring and workflow that make the engine useful for a particular journey.

Modern LangChain centres on small building blocks. Begin with a chat model and messages. Add structured output when code needs named fields. Add retrieval when answers need external documents. Add an agent only when the model genuinely must choose a tool. LangChain agents run on LangGraph, but you do not need to learn LangGraph before making your first model call.

## Core Explanation

<LangChainBuildingBlocks />

Read the visual from left to right. **Messages** preserve roles. The **prompt** defines the job. The **model** produces content or selects an action. **Structured output** makes the result usable by software. The **harness** coordinates the extra capabilities needed for a complete application.

Older tutorials may emphasise “output parsers.” They remain useful when parsing text or composing custom pipelines, but for new applications prefer a provider-supported structured-output interface when available. The result is easier to validate than free-form text.

The official diagram makes one distinction easy to remember: the model sits at the centre, while prompts, context, memory and tools belong to the surrounding harness. A basic application may use only the model and messages; add the other pieces only when the use case needs them.

## Types / Components

| Component | Beginner meaning | Use it when |
|---|---|---|
| Messages | Role-labelled conversation items | Instructions and user content must stay separate |
| Chat model | Standard interface to an LLM provider | The application needs generation or classification |
| Structured output | A validated Python result shape | Code must consume named fields |
| Retriever | Finds relevant external evidence | Answers depend on documents or current knowledge |
| Tool | A bounded Python capability | The model must request an operation |
| Agent harness | Coordinates model, tools and state | The next action cannot be fixed in advance |

## Tool / Technology Comparison

| Approach | Best fit | Trade-off |
|---|---|---|
| Provider SDK | One or two stable model calls | Least abstraction, more provider-specific code |
| LangChain model interface | Structured, portable application calls | Adds a framework dependency |
| LangChain agent | Dynamic tool selection | Requires stronger limits and observation |
| LangGraph | Explicit durable state and branching | More design work, better workflow control |

## Real-World Examples

- **Support routing:** the input is a customer message; the output is a validated category and priority that Python can route.
- **Policy assistant:** the input is an employee question; retrieval finds approved policy paragraphs before the model writes an answer.
- **Operations diagnosis:** an engineer asks why a service is unhealthy; an agent may choose a read-only log or status tool and return the observation.
- **Release review:** traces show the prompt, retrieved evidence, model response and tool calls so an engineer can investigate a failure.

## Use Cases

**Backend developer:** use structured output to convert text into a result your API can validate. **AI application engineer:** connect retrieval and tools through consistent interfaces. **QA engineer:** replay fixed cases and inspect the exact model/tool path. **Platform or SRE engineer:** trace latency, failures and token usage across a request.

Use a provider SDK directly when the feature makes one or two stable model calls and you value the smallest dependency surface. Consider LangChain when repeated application concerns—schemas, retrieval, tools, state or tracing—are making your own integration code difficult to maintain.

Avoid adding an agent simply because it sounds advanced. If the steps are known in advance, ordinary application code is often clearer and safer. Agents become valuable when the model must choose dynamically among actions.

## A minimal mental model in Python

```python
from langchain.chat_models import init_chat_model

model = init_chat_model("provider:model-name")
response = model.invoke([
    {"role": "system", "content": "Explain concepts for a beginner."},
    {"role": "user", "content": "Explain RAG using one analogy."},
])

print(response.content)
```

<LangChainCodeOutcome variant="invoke" />

The provider and model name are configuration choices. `invoke` accepts messages and returns an AI message. Your application decides what happens next: display it, validate it, store it or feed it into another controlled step.

## What LangChain does not solve automatically

<Mistakes>

- Assuming a framework prevents hallucinations.
- Using an agent for a fixed sequence that ordinary code could express.
- Hiding business rules inside a long prompt instead of enforcing them in code.
- Treating a successful API response as a correct business answer.
- Copying examples written for older LangChain releases without checking current documentation.

</Mistakes>

## Key Takeaways

<Takeaways>

- LangChain is an application framework, not an LLM.
- Start with a direct model call; add retrieval or agents only when the problem requires them.
- Messages carry role-based context, while structured output creates a software-friendly contract.
- Framework abstractions improve composition, not factual correctness by themselves.
- Current documentation matters because LangChain APIs evolve quickly.

</Takeaways>
