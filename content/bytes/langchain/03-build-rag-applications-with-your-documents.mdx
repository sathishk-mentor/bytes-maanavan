## Start from Basics

Suppose your company changes its leave policy today. The LLM was not trained on that private update, so asking the model directly invites a guess. Copying the entire policy into every prompt is also slow, expensive and eventually too large.

Retrieval-Augmented Generation (RAG) solves a narrower problem: **find the few relevant passages first, then give only those passages to the model as evidence.** It does not retrain the model and it does not magically make every answer correct.

Without retrieval, a model cannot reliably know your current leave policy, internal course catalogue or private product manual. With retrieval, the application can supply the relevant passages and preserve links or document identifiers for citation.

## Core Explanation

RAG has two different lifecycles. **Indexing** happens when documents are prepared or updated. **Answering** happens each time a user asks a question. Keeping these phases separate prevents a common beginner confusion: documents are not split and embedded from scratch for every question.

```text
documents → load → split → embed → store vectors + text + metadata
```

1. **Load:** read supported sources such as PDF, HTML or text.
2. **Split:** create chunks small enough to retrieve precisely but large enough to preserve meaning.
3. **Embed:** convert each chunk into a numerical representation of semantic meaning.
4. **Store:** save vectors alongside original text and metadata.

Metadata should preserve source, section, version and access scope. A vector without its source context is difficult to cite, filter or govern.

### Query-time retrieval

```text
question → embed → similarity search → relevant chunks → model → cited answer
```

The retriever finds candidate chunks; the model synthesises an answer. Retrieval quality and generation quality are different problems. A fluent answer can still be wrong if the retriever selected irrelevant or outdated text.

## Architecture / Flow Diagram

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_core.vectorstores import InMemoryVectorStore

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,
    chunk_overlap=120,
)
chunks = splitter.split_documents(documents)

vector_store = InMemoryVectorStore(OpenAIEmbeddings())
vector_store.add_documents(chunks)

retriever = vector_store.as_retriever(search_kwargs={"k": 4})
evidence = retriever.invoke("How many casual leave days are available?")
```

## Types / Components

| Component | Job | Beginner check |
|---|---|---|
| Loader | Reads text and source metadata | Did page and version survive? |
| Splitter | Creates retrievable passages | Does each chunk preserve one useful idea? |
| Embedding model | Represents semantic meaning | Are indexing and query models compatible? |
| Vector store | Searches stored chunks | Are filters and access scope applied? |
| Retriever | Returns candidate Documents | Are results relevant and current? |
| Generator | Writes from retrieved evidence | Can it abstain when evidence is weak? |

## Tool / Technology Comparison

| Pattern | Best use | Limitation |
|---|---|---|
| Keyword search | Exact names and identifiers | Misses semantic matches |
| Vector search | Meaning-based discovery | Similarity is not truth |
| Hybrid search | Exact and semantic ranking | More evaluation complexity |
| Agentic RAG | Dynamic retrieval decisions | Higher latency and control needs |

## Real-World Examples

An engineer asks, “How many casual leave days are available?” The retriever returns the current leave-policy paragraph and its document metadata. The model writes an answer using that evidence. If no relevant passage is found, the safe result is “I could not find this in the approved policy”—not a confident guess.

For product support, the same pattern searches the correct manual version. For an incident assistant, it searches approved runbooks. In every case, access filters must run before evidence reaches the model.

An employee assistant answers from the current policy version. A support assistant retrieves the correct product edition. A compliance assistant filters evidence by region and access. In all three cases, the application returns verifiable source IDs with the answer.

An in-memory store is suitable for learning, not durable production storage. Choose a production vector store based on scale, filtering, latency, operations and data-governance requirements—not popularity alone.

## Use Cases

A document assistant should return more than prose:

```python
class GroundedAnswer(BaseModel):
    answer: str
    source_ids: list[str]
    insufficient_evidence: bool
```

Instruct the system to say when evidence is insufficient. Then verify that returned source identifiers actually belong to retrieved chunks; never let the model invent a citation URL.

## RAG quality checks

Test the system at three layers:

| Layer | Question | Useful measure |
|---|---|---|
| Retrieval | Did we find the evidence? | Recall at k |
| Generation | Is the answer supported? | Faithfulness / citation check |
| Product | Did the user complete the task? | Resolution or escalation rate |

Also test adversarial documents, conflicting versions, empty retrieval, access-controlled content and questions that should be refused.

## Common mistakes

<Mistakes>

- Splitting every document with one arbitrary chunk size.
- Removing headings and source metadata during ingestion.
- Mixing documents a user may access with documents they may not.
- Asking the model to create citations that were not supplied by retrieval.
- Evaluating only answer fluency instead of retrieval and evidence quality.

</Mistakes>

## Interview bit

<ThemeCard title="Explain a RAG pipeline." badge="CAREER">

**Strong answer:** I separate indexing from query-time retrieval. During indexing I load, chunk, embed and store text with source and access metadata. At query time I retrieve relevant chunks, give only authorised evidence to the model and require a grounded answer with validated source identifiers. I evaluate retrieval recall separately from answer faithfulness.

</ThemeCard>

## Key Takeaways

<Takeaways>

- RAG supplies external context at request time; it is not model training.
- Chunking and metadata directly affect retrieval quality and governance.
- Vector search returns candidates, not guaranteed truth.
- Citations must be bound to retrieved sources by application code.
- Evaluate retrieval, generation and product outcomes separately.

</Takeaways>

## Final Thought + Next Path

> RAG does not give the model permanent knowledge. It finds the best permitted evidence for the current question and places that evidence inside the request. Next, you will turn retrieval and other bounded capabilities into tools an agent can choose deliberately.
