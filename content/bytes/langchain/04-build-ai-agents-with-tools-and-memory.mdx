## What makes this an agent?

A fixed workflow follows steps chosen by the developer. An agent uses a model to decide which available action to take next. The loop is usually: receive goal, reason over state, call a tool, observe its result and continue until a final answer or stop condition.

“Autonomous” does not mean unlimited. A dependable agent has a narrow purpose, carefully described tools, access checks, iteration limits and human approval for consequential actions.

<OfficialLangChainDiagram variant="agent-loop" />

Read the official loop clockwise: a request reaches the model; the model either returns a result or selects an action; the tool executes; its observation returns to the model. The loop continues only until the task is complete or your application’s limit is reached.

## Define a bounded tool

```python
from langchain.tools import tool

@tool
def search_course_catalogue(topic: str) -> str:
    """Return matching published courses for a learning topic."""
    return catalogue.search(topic)
```

The docstring is part of the tool contract the model sees. Give tools specific names, typed arguments and narrow outputs. Do not expose a generic “run SQL” or “call any URL” tool when the task only needs catalogue search.

## Create the agent

```python
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="openai:gpt-4.1-mini",
    tools=[search_course_catalogue, get_enrolment_status],
    system_prompt=(
        "Help learners choose and access courses. "
        "Never purchase, refund or modify an account."
    ),
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": "learner-1042"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "Find a beginner Docker course."}]},
    config,
)
```

Use a durable checkpointer in production. An in-memory saver is appropriate only for local learning because state disappears when the process restarts.

## Memory is state, not intelligence

Short-term memory stores the current thread’s state so later requests can refer to earlier messages. Long conversations can exceed the model context window, increase cost and reduce attention quality. Production agents need a strategy to trim, summarise or selectively retain context.

Do not mix users by reusing a thread identifier. Treat thread ownership as an authorisation concern, not merely a naming convention.

## Real-time scenario: “continue my learning path”

<Scenario title="Context helps; authority still belongs to the application">

A learner first asks for a beginner Docker course and later says, “Show the second option.” Thread state helps interpret “second option.” The agent may search the catalogue and check whether the learner already has access. It must not purchase the course, reveal another learner’s enrolment or alter the account unless a separately authorised workflow and explicit confirmation allow that action.

</Scenario>

## Tool loop versus deterministic workflow

| Choose an agent when | Choose ordinary workflow code when |
|---|---|
| The correct next action depends on the request | The steps are known in advance |
| Several tools may be needed in different orders | Every request follows the same sequence |
| Natural-language ambiguity is central | Rules can be expressed directly |
| A model’s routing value exceeds its added risk | Predictability and auditability dominate |

Hybrid designs are common: an agent chooses a bounded path, while deterministic services validate and execute important actions.

## Guardrails that matter

- Validate tool arguments before execution.
- Authorise every data access using the authenticated user, not the model’s claim.
- Set time, cost and iteration budgets.
- Require approval for payments, deletion, messages or account changes.
- Log tool names, safe metadata and outcomes without leaking secrets.
- Test prompt injection arriving through retrieved content and tool results.

## Common mistakes

<Mistakes>

- Calling chat history “memory” without defining scope, retention and ownership.
- Giving the agent broad tools because they are convenient during a demo.
- Trusting tool arguments generated by the model without validation.
- Allowing an agent to loop indefinitely.
- Assuming a system prompt is an access-control mechanism.

</Mistakes>

## Interview bit

<ThemeCard title="How do tools and memory work in a LangChain agent?" badge="CAREER">

**Strong answer:** `create_agent` runs a model-driven tool loop. Tools expose narrow typed capabilities; their results return as messages for the next decision. A checkpointer persists thread-scoped state for short-term memory. I keep authorisation, validation, budgets and approval gates in application code because prompts and model decisions are not security boundaries.

</ThemeCard>

## Key takeaways

<Takeaways>

- An agent dynamically chooses actions; a workflow follows predetermined steps.
- Tool descriptions, schemas and permissions form the agent’s action boundary.
- Short-term memory is persisted thread state and needs lifecycle controls.
- Consequential actions require deterministic validation and approval.
- Start narrow and expand capability only after observing evidence.

</Takeaways>
