## Start from Basics

In Byte 03, retrieval supplied knowledge from documents. Memory solves a different problem: it supplies relevant information from the **current conversation**.

Consider two messages:

1. “My transaction limit is ₹50,000.”
2. “Can I increase it?”

The word **it** has no useful meaning by itself. A chat model is stateless between API calls unless the application sends earlier messages again. LangChain memory helps the application organise that history by conversation thread.

<Scenario title="Easy Tanglish connection">

Call centre agent previous notes paarkama each time “problem enna?” nu ketta frustrating-a irukkum. Conversation memory is like the agent opening the correct customer’s current call notes. It is not the bank’s permanent account database.

</Scenario>

## Core Explanation

Four terms are enough to begin:

| Term | Beginner meaning | Example |
|---|---|---|
| Message history | Ordered user and AI messages | Question, answer, follow-up |
| Thread | One conversation boundary | `customer-42-support-7` |
| Thread ID | Key used to resume the correct thread | Never reuse across customers |
| Checkpointer | Stores and reloads thread state | Memory locally; database in production |

Short-term memory belongs to one thread. Long-term memory stores information that may be useful across different conversations. A customer’s verified balance, identity or transaction history belongs in an authorised business system—not in chat memory.

## Architecture / Flow Diagram

```text
Turn 1                             Turn 2
“Limit is ₹50,000”                 “Can I increase it?”
        │                                  │
        ▼                                  ▼
thread_id: customer-42 ──► checkpointer ──► load earlier messages
                                                   │
                                                   ▼
                                  model receives both turns
                                                   │
                                                   ▼
                                  “it” = transaction limit
```

The thread ID is an isolation boundary. Authentication must prove that the current user is allowed to resume that thread. A random-looking ID alone is not authorisation.

## Types / Components

For current LangChain agents, attach a checkpointer when creating the agent:

```python
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="provider:model-name",
    tools=[],
    system_prompt="Explain account policies using simple language.",
    checkpointer=InMemorySaver(),
)

thread = {"configurable": {"thread_id": "customer-42"}}

agent.invoke(
    {"messages": [{"role": "user", "content": "My limit is ₹50,000."}]},
    thread,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "Can I increase it?"}]},
    thread,
)
```

`InMemorySaver` is for learning and local tests. Its content disappears when the process restarts. Production systems need a durable checkpointer supported by the application’s availability, access-control and retention requirements.

## Tool / Technology Comparison

| Approach | What the model receives | Best fit | Main risk |
|---|---|---|---|
| Stateless | Current message only | Independent classification | Follow-ups lose context |
| Full history | Every earlier message | Short conversations | Cost and distraction grow |
| Sliding window | Recent messages | Longer support threads | Older useful detail may disappear |
| Summarised history | Compact conversation summary | Very long sessions | Summary may omit an important fact |

Do not choose a memory strategy only by token cost. Test whether users can still complete the actual task after trimming or summarisation.

## Real-World Examples

Imagine the fictional **PaisaWise** support assistant:

- Turn 1: “Why was transfer TX-104 delayed?”
- Turn 2: “Was it completed now?”
- Memory resolves **it** to transaction `TX-104`.
- A separate authorised tool—not memory—checks the current transaction status.

This distinction prevents a dangerous error: remembering an old status is not the same as reading the live system of record.

## Use Cases

- **Backend engineer:** map authenticated sessions to thread IDs and durable storage.
- **AI application engineer:** decide what history, summary and retrieved context enter each model call.
- **QA engineer:** test pronouns, topic changes, long conversations and cross-user isolation.
- **Platform/SRE engineer:** monitor state-store latency, failures, retention and storage growth.

## Common mistakes

<Mistakes>

- Reusing one thread ID for multiple users.
- Sending unlimited history until cost and latency become unpredictable.
- Storing OTPs, secrets or unnecessary personal data in messages.
- Treating conversation history as the source of truth for balances or order status.
- Assuming a summary preserves every business-critical detail.

</Mistakes>

## Key Takeaways

<Takeaways>

- Model calls are stateless unless the application supplies earlier context.
- A thread groups related turns; a checkpointer persists and reloads its state.
- Thread ownership must be authorised, not merely guessed from an ID.
- Short-term memory and long-term business data have different responsibilities.
- Long conversations require trimming, summarisation or selective context.
- In-memory storage is suitable for learning, not resilient production state.
- Retrieval brings external knowledge; memory brings conversational continuity.
- Test isolation and forgotten-context cases before release.

</Takeaways>

## Final Thought + Next Path

> Memory does not make the model permanently intelligent. It is controlled context management: save the correct messages, reload them for the correct thread and forget what is no longer useful. In Byte 05, the assistant will move beyond remembering and request bounded tools for live information.
