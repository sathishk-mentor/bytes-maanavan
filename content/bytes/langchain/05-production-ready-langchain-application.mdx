## Start from Basics

A model can write, “I checked your balance,” without checking anything. A **tool** is the real Python function that performs a bounded operation. An **agent** is a model running inside a harness that can request an allowed tool, receive its observation and continue until the task is complete.

Do not start with an agent when normal Python already knows the steps. Use a fixed chain for `prompt → model → schema`. Consider an agent when the correct next tool genuinely depends on the user’s request.

## Core Explanation

The beginner mental model has five parts:

1. **Goal:** what the user wants.
2. **Tool list:** operations the application permits.
3. **Decision:** the model chooses whether a tool is needed.
4. **Observation:** application code executes the tool and returns its result.
5. **Stop:** the agent answers, reaches a limit or requests human approval.

The model does not directly enter your database. LangChain passes tool definitions to the model, validates the requested arguments and runs the Python function through the agent harness.

## Architecture / Flow Diagram

```text
User goal
   │
   ▼
Agent model ── chooses ──► approved tool
   ▲                           │
   │                           ▼
   └──── observation ◄── application executes
   │
   ├── enough evidence ──► final answer
   └── consequential action ──► human approval
```

The loop needs a stopping condition. More iterations do not automatically mean a better answer; they may mean repeated cost, latency or an unsafe retry.

## Types / Components

First create one read-only tool:

```python
from langchain.tools import tool

@tool
def check_balance(account_id: str) -> str:
    """Return the current available balance for an authorised account ID."""
    # Learning stub. A real implementation verifies the caller first.
    balances = {"PW-104": 24500}
    amount = balances.get(account_id)
    return "Account not found" if amount is None else f"₹{amount:,}"
```

The name, type hints and docstring form the tool contract. A vague tool such as `get_data(query: str)` gives the model too much freedom and gives reviewers too little clarity.

Create the agent with the current LangChain API:

```python
from langchain.agents import create_agent

agent = create_agent(
    model="provider:model-name",
    tools=[check_balance],
    system_prompt=(
        "Help with account questions. Use read-only tools when needed. "
        "Never transfer money, issue refunds or claim an action succeeded "
        "unless a tool confirms it."
    ),
)

result = agent.invoke({
    "messages": [
        {"role": "user", "content": "Check the balance for PW-104."}
    ]
})

print(result["messages"][-1].content)
```

<LangChainCodeOutcome variant="tool" />

Expected sequence: the model requests `check_balance`, Python executes it, the tool observation returns and the model writes the final response. A drafted request is not a completed external action.

## Tool / Technology Comparison

| Pattern | Who chooses the next step? | Best fit | Predictability |
|---|---|---|---|
| Python function | Developer | One operation | Highest |
| Fixed chain | Developer | Known sequence | High |
| Router | Classifier/rules | Choose one known path | Medium-high |
| Agent | Model | Dynamic tool sequence | Lower; needs stronger controls |

Choose the least autonomous pattern that solves the problem. “Agent” is an architectural trade-off, not an upgrade badge.

## Real-World Examples

In the fictional **PaisaWise** application:

- “What is my current balance?” may use a read-only lookup tool.
- “Show my last three transactions” may use a separately scoped history tool.
- “Transfer ₹5,000” must not reuse either read tool; it needs identity checks, policy validation and explicit approval.
- If the lookup fails, the agent must report failure instead of inventing a balance.

For an SRE assistant, the same pattern allows health checks and log searches but keeps restart, scaling and deletion tools behind approval.

## Use Cases

- **Backend engineer:** implement tools with authentication, validation and idempotency.
- **AI application engineer:** design tool descriptions, agent prompts and stop rules.
- **QA engineer:** test wrong-tool selection, invalid arguments, timeouts and repeated loops.
- **DevOps/SRE:** expose read-only diagnostics and trace model/tool latency.
- **Security engineer:** separate read and write permissions and review approval boundaries.

## Guardrails that matter

<Mistakes>

- Giving a broad SQL, shell or arbitrary-URL tool to a narrow support agent.
- Treating the user’s account ID as proof that they own the account.
- Allowing money movement, deletion or access changes without human approval.
- Retrying a failed write and accidentally duplicating the side effect.
- Claiming “completed” when the tool returned an error or never ran.
- Logging secrets or private tool results without redaction.

</Mistakes>

## Key Takeaways

<Takeaways>

- A tool is a callable operation with a clear input and output contract.
- An agent is a model calling tools in a loop inside an application harness.
- Use deterministic Python or a chain when the steps are already known.
- Tool descriptions influence selection, but application code must enforce permission.
- Observations prove what the tool returned; model text alone proves nothing happened.
- Read and write tools need different risk controls.
- Consequential actions require approval, limits and auditable results.
- Test tool errors and stopping behaviour, not only successful answers.

</Takeaways>

## Final Thought + Next Path

> The useful agent is not the one with the most tools. It is the one that chooses among a small authorised set, reports observations honestly and stops at the right boundary. You have now connected models, prompts, retrieval, memory and tools into one explainable LangChain application path.
