## Core Concept

Recall the RAG Handbook's four stages: chunking documents, creating "meaning fingerprints" (embeddings), storing them in a searchable index, and retrieving the right pieces before answering. In our Python LangChain series, we wired this manually using Chroma. In Java, Spring AI provides a **`VectorStore`** abstraction — the same core idea, just as an interchangeable Spring Bean, and a **`QuestionAnswerAdvisor`** that automatically handles the "search, then answer" flow for you.

Think of the `VectorStore` as a plug socket — PostgreSQL/pgvector, MongoDB Atlas, Pinecone, Qdrant, and others all fit the same socket. You write your RAG logic once, and swap the underlying storage the same way you'd swap a database driver.


## How It Works Under the Hood

**Step 1: Load and store documents (usually done once, as a setup/ingestion task):**

```java
@Service
public class PolicyIngestionService {

    private final VectorStore vectorStore;

    public PolicyIngestionService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    public void ingest(List<Document> policyChunks) {
        vectorStore.add(policyChunks);
    }
}
```

`Document` here is Spring AI's representation of one chunk — conceptually identical to the "index cards" from our RAG Handbook's Byte 1.

**Step 2: Answer questions using retrieved context, via the Advisors API:**

```java
@Service
public class PolicyQAService {

    private final ChatClient chatClient;

    public PolicyQAService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder
                .defaultAdvisors(new QuestionAnswerAdvisor(vectorStore))
                .build();
    }

    public String answer(String question) {
        return chatClient.prompt()
                .user(question)
                .call()
                .content();
    }
}
```

Notice the method body looks almost identical to Byte 2's `ComplaintSummaryService`. The difference is entirely in the setup: attaching `QuestionAnswerAdvisor` means every call now automatically searches `vectorStore` for relevant chunks and includes them before the model answers — the retrieval step from our RAG Handbook happens transparently, behind this one line of configuration.

## Try It Yourself (Small Snippet)

**Configuring pgvector as the storage backend** (an `application.properties` change, connecting back to our SQL Handbook's pgvector byte):

```properties
spring.ai.vectorstore.pgvector.index-type=HNSW
spring.ai.vectorstore.pgvector.dimensions=1536
```

Notice this is the exact same `HNSW` indexing concept from our SQL Handbook's vector search byte — Spring AI isn't reinventing vector search, it's wiring Java into the same underlying pgvector technology.


## Real Company Angle

Spring AI's Advisors API and auto-configuration for vector stores like PostgreSQL/pgvector, MongoDB Atlas, Pinecone, and Qdrant reflect a broader industry pattern: Java teams don't need to build RAG pipelines from scratch. With Document ETL support that handles ingesting PDFs, S3 files, and other formats with proper chunking, enterprises can go from "raw policy PDFs" to a working, queryable knowledge base largely through configuration and a handful of service classes — rather than the substantial custom pipeline work RAG required just a couple of years ago.


## Common Mistakes

1. **Re-ingesting the same documents on every application restart** — ingestion should typically be a separate, controlled step, not something that runs automatically every time the app boots.
2. **Forgetting that chunking quality still matters in Java, exactly as covered in our RAG Handbook** — Spring AI handles the plumbing, but poor chunking still leads to poor answers, regardless of language.
3. **Assuming `QuestionAnswerAdvisor` guarantees correct answers** — as our RAG Handbook's Byte 3 covered, retrieval can still miss the right chunk, or the model can still add unsupported detail; evaluation is still necessary.
4. **Hardcoding vector dimensions incorrectly** — the `dimensions` property must match your embedding model's actual output size, or storage/retrieval will silently misbehave.

| Storage abstraction | Vector store (e.g., Chroma) | `VectorStore` interface |
| One chunk of content | `Document` object | `Document` object (same name, same idea) |

## Key Takeaways

- Spring AI's `VectorStore` interface plays the same role as Chroma/pgvector in our Python RAG series — an interchangeable storage backend for document chunks.
- `QuestionAnswerAdvisor` automates the "retrieve relevant chunks, then answer" flow, attached to `ChatClient` with one line of configuration.
- The underlying concepts — chunking, embeddings, retrieval quality, evaluation — are unchanged from our RAG Handbook; only the implementation language differs.
- Spring AI supports the same production-grade vector databases (pgvector, MongoDB Atlas, Pinecone, Qdrant) our SQL Handbook covered, so enterprise infrastructure choices carry over.
- RAG's known failure modes (stale documents, bad chunking, poor retrieval) apply just as much in Java — the language changes, the underlying discipline doesn't.


## FAQ / Knowledge Check

**Q1: What Spring AI class automates the "search documents, then answer" RAG flow?**
`QuestionAnswerAdvisor`, attached to a `ChatClient` via `.defaultAdvisors(...)`.

**Q2: Does moving RAG from Python to Java change the underlying vector database options?**
No — Spring AI supports the same production vector databases (pgvector, MongoDB Atlas, Pinecone, Qdrant, and others).

**Q3: Does using `QuestionAnswerAdvisor` eliminate the need for RAG evaluation?**
No — retrieval can still miss the right chunk and the model can still add unsupported detail; the evaluation practices from our RAG Handbook still apply.
