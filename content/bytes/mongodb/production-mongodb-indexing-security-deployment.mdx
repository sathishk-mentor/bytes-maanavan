## Production starts with known workloads

List the operations that matter:

- Find a learner by stable ID.
- Verify an active enrolment by learner and course.
- List recent conversations for one learner.
- Retrieve course content through vector search and metadata filters.
- Aggregate course completion and revenue.

Indexes, capacity and monitoring should follow these workloads—not a generic checklist alone.

## Design useful indexes

```javascript
db.learners.createIndex({ learner_id: 1 }, { unique: true })

db.enrolments.createIndex(
  { learner_id: 1, course_id: 1 },
  { unique: true }
)

db.conversations.createIndex(
  { learner_id: 1, created_at: -1 }
)
```

A compound index supports fields from left to right. The best order depends on equality filters, sort needs, range conditions and selectivity in the real workload.

## Tamil analogy: the library alphabetical guide

<Scenario title="Find the shelf without checking every book">

In a large library, an alphabetical or subject guide directs you to the correct shelf. Without it, you inspect every book. An index similarly helps MongoDB locate matching records without scanning the entire collection.

Adding a separate guide for every imaginable question consumes space and maintenance effort. Database indexes also accelerate reads at the cost of storage and additional write work.

</Scenario>

## Read an execution plan

```javascript
db.enrolments.find({
  learner_id: "LRN-1042",
  status: "active"
}).explain("executionStats")
```

Check whether the winning plan uses a suitable index, how many keys and documents were examined, how many results were returned and whether an in-memory sort appears. A plan is evidence for one query shape and dataset—not a permanent certificate of performance.

## Security is layered

| Layer | Production control |
|---|---|
| Identity | Separate database users or workload identities |
| Authorisation | Least-privilege roles for API, reporting and operations |
| Network | Private connectivity or tightly scoped access rules |
| Secrets | Secret manager and rotation; never source control |
| Encryption | TLS in transit and encryption at rest |
| Application | Input validation, access checks and bounded queries |
| Audit | Appropriate logs without leaking personal data or secrets |

Do not permit `0.0.0.0/0` as a convenient permanent production network rule. Limit administrative access and keep application credentials separate from human operator credentials.

## Transactions and consistency

MongoDB writes to one document atomically. This is one reason thoughtful embedding can simplify consistency. Use a multi-document transaction when a business rule truly requires several document changes to succeed or fail together. Keep the transaction short and handle retryable failure rather than using transactions automatically.

## Availability, backups and recovery

Replication supports availability; it does not replace backups. A mistaken deletion can replicate quickly. Define:

1. **Recovery Point Objective:** how much recent data can be lost?
2. **Recovery Time Objective:** how quickly must service return?
3. Backup schedule and retention.
4. Restore ownership and access.
5. Regular restore testing.

An untested backup is only a hope.

## Monitor signals learners can feel

- Query latency and slow operations.
- Connections and pool wait time.
- CPU, memory, storage and cache pressure.
- Replication lag and availability events.
- Index usage and collection growth.
- Vector-search latency, candidates and result quality.
- Application errors, timeouts and retry rate.

Connect technical signals to the user journey: “support answer took 12 seconds” is more actionable than an isolated infrastructure chart.

## Cost and capacity planning

Estimate document size, growth rate, read/write volume, index size, retention, backup storage and vector-search workload. Test with production-like data distribution. Avoid scaling the cluster before checking inefficient queries, excessive fields, missing limits and unused indexes.

## Production release checklist

- Schema validation and retention rules are documented.
- Critical queries have reviewed execution plans.
- The application user has least-privilege access.
- Network access and secrets are restricted.
- Timeouts, limits and connection pooling are configured.
- Backups exist and a restore has been tested.
- Dashboards and alerts map to learner-facing outcomes.
- Load, failure and recovery paths have been exercised.

## Common mistakes

<Mistakes>

- Creating indexes for every field without measuring usage.
- Treating replicas as backups.
- Running the application with an administrative database role.
- Opening network access broadly to solve a connection problem.
- Logging connection strings, prompts or personal learner data.
- Optimising infrastructure before inspecting query behaviour.

</Mistakes>

## Interview bit

<ThemeCard title="How do you prepare MongoDB for production?" badge="CAREER">

I begin with critical query shapes and data growth. I create and validate only necessary indexes with execution plans, use least-privilege roles and restricted networking, protect and rotate secrets, configure pooling and timeouts, define backup and tested recovery targets, and monitor latency, capacity, errors and slow queries against user-facing outcomes.

</ThemeCard>

## Key takeaways

<Takeaways>

- Build indexes for verified query patterns and inspect execution evidence.
- Apply least privilege across identity, network, secrets and application access.
- Replication improves availability; backups and restore tests provide recovery.
- Production readiness joins performance, security, resilience and cost.

</Takeaways>
