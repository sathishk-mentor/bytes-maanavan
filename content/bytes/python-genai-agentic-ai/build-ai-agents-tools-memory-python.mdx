The agent decides the next step, but a Python tool performs the actual operation. Keeping these responsibilities separate makes permissions, testing and evidence clearer.

## Chatbot, copilot and agent

| Pattern | Typical behaviour | Example |
|---|---|---|
| Chatbot | Produces a response | Explains a Python error |
| Copilot | Assists a human doing work | Drafts a weekend watchlist for review |
| Agent | Chooses and performs tool steps | Reads preferences, checks titles and prepares options |

An agent follows a loop: understand the goal, choose the next useful step, call a tool, observe the actual result and decide whether to continue or stop.

## Create bounded Python tools

```python
def calculate_weeks(total_hours: int, weekly_hours: int) -> int:
    if weekly_hours <= 0:
        raise ValueError("weekly_hours must be positive")
    return (total_hours + weekly_hours - 1) // weekly_hours
```

A tool definition needs a precise name, description, parameter schema and return contract. Narrow tools are easier to authorise, test and observe than a general `run_anything` tool.

## State and memory are different

**State** is what the current run needs: goal, completed steps, tool results and remaining work. **Memory** carries selected information across interactions. Store only useful, permitted information with a retention rule. Never treat an old memory as unquestionable truth.

## Read tools, write tools and approval

Reading a streaming catalogue is usually lower risk than changing a shared watchlist or renting a paid title. Separate read and write capabilities, apply least privilege and require explicit approval before consequential calls.

```python
if proposed_action.type == "rent_paid_title":
    return {
        "status": "approval_required",
        "proposal": proposed_action.model_dump(),
    }
```

The UI should show exactly what will happen, where and with which data. After approval, the agent must inspect the tool result before claiming success.

## Stopping rules

A safe agent knows when to stop. Missing information, absent permission, repeated failure or a reached step limit should return control to the learner.

Stop when the goal is complete, required information is missing, permission is absent, a risk boundary is reached, the same tool fails repeatedly or the maximum step count is reached.

Log the tool name, safe parameters, result status, latency and correlation ID. Do not log secrets or unnecessary learner content.

## Model Context Protocol

MCP is a standard way for AI applications to discover and use exposed tools and context. It can improve interoperability, but it does not make a tool trustworthy. Authentication, authorisation, validation and human approval still belong to the application and tool boundary.

## Framework or framework-free

Start with a small explicit Python loop when the workflow is narrow. Use a framework when durable state, branching, tool ecosystems, tracing or team conventions justify the added abstraction. The safety responsibilities are the same.

## Critical safety rule

<ThemeCard title="Preparation is not execution" badge="AGENT SAFETY">

Drafting an email does not mean it was sent. Preparing an event does not mean it was scheduled. Generating a payment request does not mean payment completed. An external action is complete only when the connected tool returns verifiable success.

</ThemeCard>

## Key takeaways

<Takeaways>

- Agents choose actions; tools perform bounded operations.
- State tracks the run, while memory carries selected context.
- Separate read access from consequential write access.
- Apply maximum steps, retries and clear stop conditions.
- Claim completion only from confirmed tool evidence.

</Takeaways>
