## S1 — Quick Start

A ticket list must show many tickets without duplicating each card's markup.

**You will learn:** Explain the concept, predict the visible UI result and implement one small change. **Prerequisite:** Familiarity with basic JavaScript expressions helps, but no prior React experience is required.

## S2 — Start from Basics: Familiar Scenario

Imagine a software company's customer-support dashboard. Staff read tickets, filter the list, change ticket status and navigate between records. We use this *illustrative* workflow to learn React rather than claiming it is a real company's internal application.

JSX: syntax for declaring UI. Component: capitalized function returning UI. Props: parent-to-child inputs. Children: nested UI content. Key: stable identity for items in a list. Composition: building larger views from smaller components.

## S3 — Core Explanation

Create a TicketCard once, then pass subject and priority as props. Props are read-only. Render lists using stable IDs; do not use random keys that change every render.

A useful analogy is an office display board: inputs describe which cards belong on the board and an update changes the visible board. React coordinates that display; a real backend remains responsible for permanent records and access control.

## S6 — Guided Walkthrough

This is a small standalone teaching example. For a real Vite app use the React + TypeScript template, place it in a component file, import it into App and run the development server.

```tsx
type Ticket = { id: string; subject: string; priority: string };
function TicketCard({ subject, priority }: Omit<Ticket, "id">) {
  return <article><h3>{subject}</h3><span>{priority}</span></article>;
}
export function TicketList({ tickets }: { tickets: Ticket[] }) {
  return <section>{tickets.map(t => <TicketCard key={t.id} subject={t.subject} priority={t.priority} />)}</section>;
}
```

**Expected output:** Each ticket renders a reusable subject and priority card.

**Execution explanation:** Follow the component inputs, the code decision, the changed React output and what a user can observe. Keep the example small enough to explain aloud during an interview.

## S7 — Failure Cases and Common Mistakes

Avoid mutating props or using array indexes as keys when records can reorder.

If the UI looks wrong, inspect data input, state updates, console errors and element semantics separately. Compare the expected output above with the actual browser result.

## S8 — Role-Based Application

Frontend engineers maintain design systems; reviewers ensure semantic elements and stable keys. Product managers describe the workflow outcome and acceptance criteria. A support team member can validate that the wording and action match the intended business process.

## S9 — Compare User View and System View

| What the user sees | What happens underneath |
|---|---|
| User sees multiple unique cards | Parent maps data to child instances using stable keys |
| A responsive interface | React decides which UI description to reconcile with the DOM |
| A visible result after interaction | The application determines whether data is only local or saved remotely |

## S11 — Final Thought and Next Path

1. Begin with the real user problem.
2. Separate UI from persistent backend concerns.
3. Name each component or Hook by its purpose.
4. Distinguish inputs from state.
5. Trace interactions step by step.
6. Inspect the rendered result, not only code.
7. Prefer clarity over unnecessary complexity.
8. Validate behaviour, accessibility and failure cases.
