## When the UI needs to change

A support agent clicks Resolve and expects the ticket's status label to update immediately.

**You will learn:** Explain the concept, predict the visible UI result and implement one small change. **Prerequisite:** Familiarity with basic JavaScript expressions helps, but no prior React experience is required.

## Resolving a customer-support ticket

Imagine a software company's customer-support dashboard. Staff read tickets, filter the list, change ticket status and navigate between records. We use this *illustrative* workflow to learn React rather than claiming it is a real company's internal application.

State: component memory. useState: Hook for render-dependent data. Setter: function that requests an update. Event handler: callback for interaction. Re-render: recalculation of UI. Snapshot: state values captured per render.

## Understanding state and render snapshots

Use the setter from useState instead of changing the state variable directly. Treat arrays and objects as immutable. State represents UI memory, not permanent server storage.

A useful analogy is an office display board: inputs describe which cards belong on the board and an update changes the visible board. React coordinates that display; a real backend remains responsible for permanent records and access control.

## Build the Support Dashboard: Step-by-Step Code

State is React's memory for values that change on screen. Event handlers request changes; React renders the updated status.

**Connected learning:** These files belong to one `support-desk` application. Each code step updates or adds to the same project. The final code from this Byte is the starting point for the next Byte. **Project checkpoint:** Click → handler → setter → render.

### Step 1 — Extend the ticket type

```tsx
// src/components/TicketCard.tsx
export type Ticket = { id: number; subject: string; priority: 'High' | 'Medium' | 'Low'; status: 'open' | 'resolved' };
```

**Expected result:** Status is now an explicit part of every ticket.

### Step 2 — Update initial records

```tsx
// src/data/tickets.ts
import type { Ticket } from '../components/TicketCard';
export const initialTickets: Ticket[] = [
 {id:101,subject:'Login problem',priority:'High',status:'open'},
 {id:102,subject:'Payment question',priority:'Medium',status:'open'}
];
```

**Expected result:** Both example tickets start as open.

### Step 3 — Create an interactive card

```tsx
// src/components/TicketCard.tsx
export default function TicketCard({ ticket, onToggle }: { ticket: Ticket; onToggle: (id: number) => void }) {
  return <article><strong>#{ticket.id} {ticket.subject}</strong>
    <p>Priority: {ticket.priority} · {ticket.status}</p>
    <button onClick={() => onToggle(ticket.id)}>{ticket.status === 'open' ? 'Resolve' : 'Reopen'}</button>
  </article>;
}
```

**Expected result:** The card asks its parent to change the selected ticket.

### Step 4 — Manage state in App

```tsx
// src/App.tsx
import { useState } from 'react';
import TicketCard from './components/TicketCard';
import { initialTickets } from './data/tickets';
export default function App() {
 const [tickets, setTickets] = useState(initialTickets);
 function toggle(id: number) {
   setTickets(current => current.map(t => t.id === id ? {...t,status: t.status === 'open' ? 'resolved' as const : 'open' as const} : t));
 }
 return <main><h1>Support Desk</h1>{tickets.map(t => <TicketCard key={t.id} ticket={t} onToggle={toggle} />)}</main>;
}
```

**Expected result:** Click Resolve or Reopen and see only the chosen ticket's status change.


### Try it yourself

Display the number of open tickets above the list using tickets.filter(...).length; do not duplicate it in separate state.

## Common state and event mistakes

Never mutate an object in state in place and expect React to notice. For updates based on previous state, prefer the functional setter.

If the UI looks wrong, inspect data input, state updates, console errors and element semantics separately. Compare the expected output above with the actual browser result.

## Managing UI state in real teams

Frontend developers connect business interactions to state; QA engineers test transitions. Product managers describe the workflow outcome and acceptance criteria. A support team member can validate that the wording and action match the intended business process.

## What the user sees after setState

| What the user sees | What happens underneath |
|---|---|
| User sees resolved | React schedules a render after the state setter runs |
| A responsive interface | React decides which UI description to reconcile with the DOM |
| A visible result after interaction | The application determines whether data is only local or saved remotely |

## Key takeaways

1. Begin with the real user problem.
2. Separate UI from persistent backend concerns.
3. Name each component or Hook by its purpose.
4. Distinguish inputs from state.
5. Trace interactions step by step.
6. Inspect the rendered result, not only code.
7. Prefer clarity over unnecessary complexity.
8. Validate behaviour, accessibility and failure cases.

## FAQ, knowledge check and references

Does setting state change the current variable instantly? No, it schedules a new render. Does state persist after refresh? Not automatically. Can state hold arrays? Yes.

**Interview-ready explanation:** Use the setter from useState instead of changing the state variable directly.
