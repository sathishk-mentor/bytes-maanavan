## Why tasks disappear after refresh

Our To-Do List now works until the browser refreshes. React component state is memory, not permanent storage. We can keep a small personal demo list in **localStorage**, a browser feature, and use `useEffect` to synchronize changes.

**What you will build:** Milestone 4 of a small browser-based To-Do List. No backend or advanced architecture is needed.

## Saving tasks in the browser

The task list on screen is like a whiteboard. `localStorage` is a notebook where we keep a copy. When the page opens, we read the notebook. Whenever the list changes, we update the notebook.

## Effects and browser synchronization

An **Effect** runs after React has committed the UI and can synchronize with something *outside React*. `useEffect(() => { localStorage.setItem(...) }, [tasks])` says: after `tasks` changes, save a JSON representation. A lazy `useState(() => ...)` initializer reads saved tasks only at initial mounting in this client-only Vite example. `JSON.stringify` converts the array to text; `JSON.parse` reads it back. The `[tasks]` dependency tells React which reactive value the Effect uses. Not all Effects need cleanup: saving one value doesn't create a subscription. Timers and event listeners do need cleanup.

### Step 2: Read saved tasks when initializing state

**Where:** `src/App.tsx`

```tsx
// Replace the initial useState<Task[]>(initialTasks) declaration:
const [tasks, setTasks] = useState<Task[]>(() => {
  try {
    const saved = window.localStorage.getItem('my-tasks');
    return saved ? JSON.parse(saved) as Task[] : initialTasks;
  } catch {
    return initialTasks;
  }
});
```

**Expected screen/result:** Saved tasks load on a browser-only Vite app. This initial code intentionally targets client-only rendering.

### Step 3: Add a save Effect

**Where:** `src/App.tsx`

```tsx
// Import useEffect alongside useState:
import { useEffect, useState } from 'react';

// Inside App, below tasks state:
useEffect(() => {
  window.localStorage.setItem('my-tasks', JSON.stringify(tasks));
}, [tasks]);
```

**Expected screen/result:** Adding or completing a task now updates browser storage after render.

## Common useEffect mistakes

- **Calling `JSON.parse` without handling failures:** Damaged text can crash initialization; use `try/catch`.
- **Effect with no dependency array:** It runs after every committed render; define the relevant dependencies.
- **Saving a derived count separately:** Compute pending tasks during render instead.
- **Mistaking browser storage for a database:** It is local to that browser and is not suitable for shared accounts or confidential data.
- **Confusing cleanup:** A one-off storage write needs no cleanup; interval/listener subscriptions do.

## Where synchronization matters

React uses the same underlying idea in many applications: a product list, a shopping basket, a learning progress page, or a dashboard. We are using task management only to keep the learning journey simple.

## Key Takeaways

1. Component state alone does not survive page refresh.
2. localStorage keeps data in one browser.
3. JSON.stringify converts task data to text.
4. JSON.parse restores saved data.
5. A lazy state initializer reads saved tasks when mounting.
6. useEffect can synchronize React state with localStorage.
7. Dependencies identify reactive values used by an Effect.
8. Browser storage is not a shared secure backend.
