## When React must synchronize with something external

A ticket list can subscribe to changes outside React, such as a browser event or live connection, and must clean up the subscription.

**You will learn:** Explain the concept, predict the visible UI result and implement one small change. **Prerequisite:** Familiarity with basic JavaScript expressions helps, but no prior React experience is required.

## Following changes outside the React component

Imagine a software company's customer-support dashboard. Staff read tickets, filter the list, change ticket status and navigate between records. We use this *illustrative* workflow to learn React rather than claiming it is a real company's internal application.

Effect: synchronization with an external system. Dependency array: reactive values used by the effect. Cleanup: teardown before replacement/unmount. Subscription: outside callback source. Stale response: outdated async result. Render: pure UI calculation.

## Understanding useEffect and cleanup

Use an Effect to synchronize with something outside React—not for ordinary calculations or click handlers. Include reactive dependencies. Clean up timers, subscriptions and stale requests when appropriate.

A useful analogy is an office display board: inputs describe which cards belong on the board and an update changes the visible board. React coordinates that display; a real backend remains responsible for permanent records and access control.

## Build an online-status example

This is a small standalone teaching example. For a real Vite app use the React + TypeScript template, place it in a component file, import it into App and run the development server.

```tsx
import { useEffect, useState } from "react";
export function OnlineBadge() {
  const [online, setOnline] = useState(navigator.onLine);
  useEffect(() => {
    const update = () => setOnline(navigator.onLine);
    window.addEventListener("online", update);
    window.addEventListener("offline", update);
    return () => { window.removeEventListener("online", update); window.removeEventListener("offline", update); };
  }, []);
  return <strong>{online ? "Online" : "Offline"}</strong>;
}
```

**Expected output:** The badge responds to browser online/offline events and unregisters listeners when removed.

**Execution explanation:** Follow the component inputs, the code decision, the changed React output and what a user can observe. Keep the example small enough to explain aloud during an interview.

## Common useEffect mistakes

Do not compute fullName from firstName and lastName inside an Effect; calculate it during rendering. Browser globals require client execution.

If the UI looks wrong, inspect data input, state updates, console errors and element semantics separately. Compare the expected output above with the actual browser result.

## Managing side effects in applications

Frontend engineers manage subscriptions and cleanup; reviewers investigate memory leaks and stale responses. Product managers describe the workflow outcome and acceptance criteria. A support team member can validate that the wording and action match the intended business process.

## What users see versus effect execution

| What the user sees | What happens underneath |
|---|---|
| User sees Online/Offline | Effect subscribes and updates state when browser connectivity events arrive |
| A responsive interface | React decides which UI description to reconcile with the DOM |
| A visible result after interaction | The application determines whether data is only local or saved remotely |

## Key takeaways

1. Begin with the real user problem.
2. Separate UI from persistent backend concerns.
3. Name each component or Hook by its purpose.
4. Distinguish inputs from state.
5. Trace interactions step by step.
6. Inspect the rendered result, not only code.
7. Prefer clarity over unnecessary complexity.
8. Validate behaviour, accessibility and failure cases.
