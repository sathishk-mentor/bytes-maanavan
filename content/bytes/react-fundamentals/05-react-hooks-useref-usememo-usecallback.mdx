## Choosing the right React Hook

A real support interface needs input focus and may have expensive filtering, but unnecessary memoization adds complexity.

**You will learn:** Explain the concept, predict the visible UI result and implement one small change. **Prerequisite:** Familiarity with basic JavaScript expressions helps, but no prior React experience is required.

## A searchable ticket interface

Imagine a software company's customer-support dashboard. Staff read tickets, filter the list, change ticket status and navigate between records. We use this *illustrative* workflow to learn React rather than claiming it is a real company's internal application.

Hook: React function providing component capabilities. useRef: persistent mutable reference. useMemo: caching calculated values. useCallback: caching function identity. Dependency: reactive input to memoization. Custom Hook: reusable Hook-based logic.

## How useRef, useMemo and useCallback differ

Use useRef for DOM focus and non-rendering mutable values. useMemo may cache expensive calculations; useCallback may preserve function identity when useful. Neither should be added to every component by default.

A useful analogy is an office display board: inputs describe which cards belong on the board and an update changes the visible board. React coordinates that display; a real backend remains responsible for permanent records and access control.

## A practical React Hooks decision flow

**Visual execution path**

```text
Need render update? useState. Need DOM focus? useRef. Expensive recalculation? consider useMemo. Stable function identity matters? consider useCallback. Otherwise write simple code.
```

## Build the Support Dashboard: Step-by-Step Code

useRef can focus a browser input. useMemo may avoid repeated expensive calculations. useCallback may preserve a function reference when a child benefits; ordinary code is often enough.

**Connected learning:** These files belong to one `support-desk` application. Each code step updates or adds to the same project. The final code from this Byte is the starting point for the next Byte. **Project checkpoint:** Search → filter → matching tickets.

### Step 1 — Add a search field

```tsx
// src/App.tsx — import useRef and useState
const searchRef = useRef<HTMLInputElement>(null);
const [query, setQuery] = useState('');
// Put this before the ticket cards in JSX:
<input ref={searchRef} value={query} onChange={e => setQuery(e.target.value)} placeholder="Search tickets" aria-label="Search tickets" />
<button onClick={() => searchRef.current?.focus()}>Focus search</button>
```

**Expected result:** Typing changes the search query; the Focus button moves keyboard focus.

### Step 2 — Filter tickets before rendering

```tsx
// src/App.tsx — compute inside App
const visibleTickets = tickets.filter(t => t.subject.toLowerCase().includes(query.toLowerCase()));
// Change tickets.map(...) to visibleTickets.map(...)
```

**Expected result:** The list narrows as the user types. Filtering can start as ordinary JavaScript.

### Step 3 — Learn memoization only if useful

```tsx
// src/App.tsx — optional optimization
const visibleTickets = useMemo(() => tickets.filter(t =>
  t.subject.toLowerCase().includes(query.toLowerCase())
), [tickets, query]);
```

**Expected result:** The cached result recalculates when tickets or query changes. Do not use this optimization without a reason.

### Step 4 — Recognize useCallback

```tsx
// Optional: import useCallback and wrap the existing toggle handler
const toggle = useCallback((id: number) => {
  setTickets(current => current.map(t => t.id === id ? {...t,status: t.status === 'open' ? 'resolved' as const : 'open' as const} : t));
}, []);
```

**Expected result:** The toggle reference remains stable; this matters mainly for memoized children or Hook dependencies.

## Common Hook optimization mistakes

Do not use refs to store displayed state or assume useMemo guarantees faster execution. Measure performance before optimizing.

If the UI looks wrong, inspect data input, state updates, console errors and element semantics separately. Compare the expected output above with the actual browser result.

## Choosing Hooks in frontend teams

Frontend engineers use references and optimize verified bottlenecks; reviewers discourage premature optimization. Product managers describe the workflow outcome and acceptance criteria. A support team member can validate that the wording and action match the intended business process.

## Visible behavior versus React internals

| What the user sees | What happens underneath |
|---|---|
| User clicks Focus | useRef points to input without scheduling a re-render |
| A responsive interface | React decides which UI description to reconcile with the DOM |
| A visible result after interaction | The application determines whether data is only local or saved remotely |

## Key takeaways

1. Begin with the real user problem.
2. Separate UI from persistent backend concerns.
3. Name each component or Hook by its purpose.
4. Distinguish inputs from state.
5. Trace interactions step by step.
6. Inspect the rendered result, not only code.
7. Prefer clarity over unnecessary complexity.
8. Validate behaviour, accessibility and failure cases.

## FAQ, knowledge check and references

Does changing ref.current re-render? No. Is useMemo always necessary? No. Is useCallback always faster? No.

**Interview-ready explanation:** Use useRef for DOM focus and non-rendering mutable values.
