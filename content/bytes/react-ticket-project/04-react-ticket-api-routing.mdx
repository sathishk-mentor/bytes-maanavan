## What you will build

A real interface must display asynchronous data, separate ticket list and detail views, and recover from failures.

**Visible checkpoint:** The mock issue list loads after a short delay; users can navigate list/detail routes and retry errors. You can study this Byte by itself, though the project can also be built progressively.

## Understand the concept first

Use React Router to map URLs to screens. Treat the server as the authoritative source once a backend exists. For this educational project use a replaceable mock adapter and simulate loading/error/retry. Do not claim the mock data is persisted centrally.

In plain language, an interface should show useful information and respond predictably to users. We begin with one small technical change before introducing more features.

## Interview Bit and Key Takeaways

**Interview question:** Why isolate an API adapter? The UI should not depend on hard-coded mock data paths when a real service is added.

**Eight takeaways:**

1. Start with a visible user goal.
2. Explain the React concept before writing code.
3. Keep UI components small and reusable.
4. Use typed interfaces and explicit data flows.
5. Validate inputs and failures clearly.
6. Test behavior from a user's perspective.
7. Avoid premature optimization and needless dependencies.
8. Confirm each project milestone works before continuing.
