## Responsibility does not move to the tool

Copilot can produce useful code and still introduce defects, insecure patterns, outdated APIs or behaviour that conflicts with requirements. The person and organization shipping the software remain responsible for the result. Review depth should match the possible impact of failure.

A text-label change and an authorization change should not use the same approval process. Increase scrutiny for identity, payments, personal data, infrastructure, destructive operations, safety-critical behaviour and compliance obligations.

## The five-gate review model

### Inspect the complete diff

Look beyond the requested function. Check configuration, dependencies, migrations, generated files and unrelated cleanup. Understand every material change before approval.

### Verify behaviour

Run automated checks and manually exercise critical user paths. Confirm negative cases—unauthorized users, invalid input, unavailable dependency and duplicate request—not only the happy path.

### Check security and privacy

Review input validation, authorization, secret handling, logging, dependency risk and data exposure. Never paste credentials, private keys, confidential source code or personal records into an unapproved service.

### Apply organizational controls

Copilot availability and features may be governed by enterprise or organization policies. Teams should document approved use, protected information, required checks and escalation paths. A personal preference cannot override organizational policy.

### Approve with accountable ownership

The final reviewer should be capable of evaluating the affected system. AI-assisted review adds coverage, but it does not become the named owner of a production decision.

## Simple analogy: the pilot owns the final checklist

An autopilot can assist, but the pilot still verifies the route, weather and aircraft before take-off. AI coding tools are similar: they accelerate preparation, while the engineer remains accountable for security, behaviour and release approval.

## Real-time scenario: risk-based code review

<Scenario title="Generated authorization middleware">

Copilot proposes middleware that checks whether a user is signed in. The endpoint, however, must also confirm that the user owns the requested invoice. The code is syntactically valid and its tests pass because the tests cover authentication but not object-level authorization.

A security-aware reviewer adds cross-account access tests and catches the gap. This demonstrates why correctness is defined by the threat model and business rule, not by compilation or confident-looking code.

</Scenario>

## Copy-and-paste review prompt

<PromptBox label="Risk-focused diff review">

Review this diff as an additional engineering reviewer.

Focus on:
1. Behaviour that changed beyond the stated requirement.
2. Authentication and object-level authorization.
3. Input validation and unsafe output handling.
4. Secrets, sensitive data and excessive logging.
5. Failure recovery, concurrency and duplicate requests.
6. Missing tests that could allow a serious regression.

For every concern, cite the relevant file and explain the failure scenario. Mark uncertainty. Do not claim the change is safe or approved.

</PromptBox>

## Release checklist

- Every material line in the diff is understood.
- Acceptance criteria are demonstrated by evidence.
- Security-sensitive behaviour received qualified review.
- Secrets and confidential data were not exposed to an unapproved tool.
- Tests cover negative paths and regression conditions.
- Dependencies and generated code were examined.
- Monitoring and rollback are appropriate to the risk.
- A named human owns the release decision.

## Common mistakes

<Mistakes>

- Assuming AI-generated code is safer because it looks conventional.
- Using Copilot review as the only pull-request approval.
- Allowing broad agent permissions without a bounded task.
- Uploading production data to make debugging easier.
- Applying identical governance to low-risk and high-risk changes.

</Mistakes>

## Interview bit

<ThemeCard title="Who is accountable for Copilot-generated code?" badge="CAREER">

The developer and organization releasing the software remain accountable. Copilot output is a proposal. I evaluate it against requirements, run tests and security checks, inspect dependencies and data exposure, and require qualified human review based on risk. AI review can add another signal, but it cannot approve its own work.

</ThemeCard>

## Key takeaways

<Takeaways>

- Copilot assistance does not transfer engineering accountability.
- Review depth should increase with potential impact.
- Passing tests are necessary evidence, not complete assurance.
- Organizational policy governs approved data and capabilities.
- Human approval remains the final production gate.

</Takeaways>
