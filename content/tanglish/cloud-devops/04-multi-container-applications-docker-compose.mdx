## ஏன் Docker Compose தேவை?

Real application பொதுவாக single container மட்டும் கொண்டிருக்காது. Food-delivery app-ல் customer frontend, order API, database மற்றும் notification service ஆகியவை தனித்தனி responsibilities-ஐ கையாளும். ஒவ்வொன்றையும் நீண்ட `docker run` command மூலம் start செய்தால் configuration தவறவிடப்படலாம்; மற்றொரு developer அதே setup-ஐ reproduce செய்வதும் கடினம்.

Docker Compose எல்லா services, network, volume, port மற்றும் health check-ஐ ஒரே readable file-ல் declare செய்ய உதவும்.

## Connected application எப்படி இருக்கும்?

<HandbookLearningVisual variant="dockerCompose" />

Browser `localhost:3000` மூலம் frontend-ஐ அணுகும். Frontend, Compose network-ல் `http://order-api:8000` என்ற முகவரியில் API-ஐ அழைக்கும். API, `postgres:5432` என்ற service name மூலம் database-ஐ அணுகும்.

## Practical `compose.yaml`

```yaml
services:
  order-api:
    build: ./api
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://app:app@postgres:5432/orders
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: orders
    volumes:
      - order-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  order-data:
```

இது learning configuration மட்டும். Real production password-ஐ file-ல் hardcode பண்ணக்கூடாது.

## முக்கியமான networking rule

Container-க்குள் `localhost` என்றால் அந்த same container. அது மற்ற service இல்லை. அதனால் API database-ஐ `localhost:5432` மூலம் அல்ல, `postgres:5432` மூலம் access பண்ண வேண்டும்.

## `depends_on` என்பது business readiness அல்ல

Process start ஆனது service ready என்று அர்த்தம் இல்லை. Health check readiness-க்கு better signal கொடுக்கும். ஆனாலும் service later fail ஆகலாம்; application timeout, bounded retry மற்றும் clear error handle பண்ண வேண்டும்.

## முழு stack-ஐ operate செய்வது

```bash
docker compose up --build
docker compose ps
docker compose logs -f order-api
docker compose exec order-api sh
docker compose down
```

`docker compose down -v` named volumes-ஐயும் நீக்கும். Database data-ஐ உண்மையாக delete செய்ய விரும்பும்போது மட்டுமே இதைப் பயன்படுத்துங்கள்.

## Real-time analogy: restaurant team

<Scenario title="One order, multiple specialised stations">

Restaurant-ல் counter, kitchen, pantry மற்றும் billing ஆகியவை தனித்தனி stations. Customer experience ஒன்று என்றாலும் ஒவ்வொரு station-க்கும் தெளிவான பெயரும் பொறுப்பும் இருக்கும். Compose அந்த operating plan போன்றது—எந்த services இருக்கின்றன, அவை எப்படி இணைகின்றன, எது முதலில் ready ஆக வேண்டும் என்பதை வரையறுக்கிறது.

</Scenario>

## Debug செய்யும் சரியான order

1. `docker compose config` மூலம் resolved configuration-ஐப் பாருங்கள்.
2. `docker compose ps` மூலம் service மற்றும் health state-ஐப் பாருங்கள்.
3. Failed request-ஐ பெற்ற service-ன் logs-ஐ முதலில் பாருங்கள்.
4. Container-to-container URL-ல் தவறாக `localhost` பயன்படுத்தப்பட்டுள்ளதா என்று சரிபாருங்கள்.
5. Environment variables மற்றும் database migration-ஐ verify செய்யுங்கள்.

## Common mistakes

<Mistakes>

- Another container-ஐ `localhost` மூலம் call செய்வது.
- எல்லா internal ports-ஐ host-க்கு publish செய்வது.
- Startup order-ஐ readiness guarantee என்று நினைப்பது.
- Production secrets-ஐ `compose.yaml`-ல் எழுதுவது.
- `docker compose down -v` effect புரியாமல் database volume delete செய்வது.

</Mistakes>

## Interview-ல் எப்படி விளக்குவது?

<ThemeCard title="Docker Compose-ல் services எப்படி communicate செய்கின்றன?" badge="CAREER">

Compose application-க்கு default network உருவாக்குகிறது. அந்த network-ல் service names DNS names-ஆக செயல்படுகின்றன. Internal traffic container port-ஐப் பயன்படுத்தும்; host வழியாக access தேவைப்படும் service-க்கு மட்டும் port publish செய்யப்படும். Started container ready என்று assume செய்யாமல் health checks மற்றும் application-level retry பயன்படுத்துவேன்.

</ThemeCard>

## நினைவில் வைக்க வேண்டிய key points

<Takeaways>

- Compose multi-container application-ஐ version-controlled configuration-ஆக describe செய்யும்.
- Service name தான் internal DNS name.
- Health checks startup coordination improve செய்யும்; runtime resilience-ஐ replace பண்ணாது.
- Data persist ஆக named volume தேவை.
- Local Compose design production architecture-க்கு starting point மட்டும்.

</Takeaways>
