## First request ஏன் final requirement இல்லை?

Customer “AI dashboard வேண்டும்” என்று கேட்கலாம். Actual problem delayed data entry, unclear ownership அல்லது manual approval bottleneck ஆக இருக்கலாம். Requested solution-க்கு முன்னால் desired outcome மற்றும் current workflow-ஐ understand பண்ண வேண்டும்.

## Presentation slide அல்ல; real work map பண்ணுங்க

Workflow map-ல் trigger, actor, input, action, system, decision, exception, handoff, wait time மற்றும் output capture பண்ணுங்க. Stated process மட்டுமல்ல; actual users என்ன workaround செய்கிறார்கள் என்பதையும் observe பண்ணுங்க.

## Easy analogy: prescribe செய்வதற்கு முன் diagnose

<Scenario title="Symptom மற்றும் root cause different">

Doctor fever கேட்டவுடன் random medicine prescribe பண்ண மாட்டார். History, symptoms, tests மற்றும் risk பார்க்கிறார். FDE-வும் feature request-ஐ symptom-ஆக எடுத்துக் கொண்டு workflow evidence மூலம் root constraint கண்டுபிடிக்க வேண்டும்.

</Scenario>

## Real-time scenario: invoice exceptions

Finance team “invoice AI automation” கேட்கிறது. Observation-ல் most invoices automatic-ஆ process ஆகிறது; delay only missing purchase order, tax mismatch மற்றும் duplicate vendor cases-ல் வருகிறது. Thin solution every invoice-ஐ automate செய்வதற்கு பதில் exception classification மற்றும் reviewer evidence focus பண்ணும்.

## Problem frame build பண்ணுவது

**For [user], when [trigger], current workflow causes [measured problem] because [evidence-backed constraint]. We will improve [metric] while preserving [safety/business boundary].**

Assumption, observation மற்றும் confirmed fact-ஐ separate பண்ணுங்க. Missing evidence-க்கு owner மற்றும் next discovery action assign பண்ணுங்க.

## Architecture முன் success define பண்ணுங்க

Cycle time, error rate, manual touches, approval delay அல்லது adoption rate போன்ற baseline மற்றும் target metrics define பண்ணுங்க. “AI response generated” business success metric இல்லை.

## Discovery anti-patterns

<Mistakes>

- Senior stakeholder explanation மட்டும் கேட்டு frontline work observe பண்ணாதது.
- Happy path மட்டும் map செய்து exceptions ignore பண்ணுவது.
- Desired technology-ஐ problem statement-ல் force பண்ணுவது.
- Baseline இல்லாமல் improvement claim பண்ணுவது.
- Data access, policy மற்றும் owner constraints late-ஆ discover பண்ணுவது.

</Mistakes>

## Interview-ல் எப்படி explain பண்ணுவது?

<ThemeCard title="FDE discovery எப்படி நடத்துவீங்க?" badge="CAREER">

Stakeholder goal-ஐ capture செய்து frontline workflow-ஐ observe பண்ணுவேன். Actors, systems, decisions, exceptions மற்றும் wait states map செய்து data மூலம் main constraint validate பண்ணுவேன். Baseline, target மற்றும் safety boundary கொண்ட problem frame agree செய்த பிறகு thin production slice design பண்ணுவேன்.

</ThemeCard>

## நினைவில் வைக்க வேண்டிய key points

<Takeaways>

- First feature request ஒரு clue; final requirement இல்லை.
- Actual workflow exceptions மற்றும் handoffs-ல் reveal ஆகும்.
- Evidence-backed problem frame architecture-ஐ guide பண்ணும்.
- Baseline இல்லாமல் outcome prove பண்ண முடியாது.
- Discovery risk மற்றும் unnecessary build-ஐ reduce பண்ணும்.

</Takeaways>
