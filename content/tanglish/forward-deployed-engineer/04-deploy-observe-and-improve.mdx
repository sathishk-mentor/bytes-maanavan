## Deployment-ல் assumptions evidence-ஆக மாறும்

Local demo expected input-ல் work ஆகலாம். Production-ல் real users, messy data, latency, permission, integration failure மற்றும் unexpected behaviour வரும். Deployment finish line இல்லை; learning loop-ன் start.

## Four layers of evidence

1. **System:** Availability, latency, error, resource use.
2. **AI quality:** Groundedness, accuracy, abstention, unsafe output.
3. **Workflow:** Adoption, override, handoff, time saved.
4. **Outcome:** Cycle time, error reduction, customer/business value.

System healthy ஆனாலும் users output trust செய்யவில்லை என்றால் deployment successful இல்லை.

## Easy analogy: healthy engine மட்டும் journey இல்லை

<Scenario title="Bus engine okay; route useful-ஆ?">

Bus engine perfect-ஆ run ஆனாலும் wrong route, late arrival அல்லது empty service இருந்தால் passenger outcome கிடைக்காது. Application uptime மட்டும் பார்க்காமல் user workflow மற்றும் intended result-ஐ measure பண்ண வேண்டும்.

</Scenario>

## Real-time scenario: support response assistant

Assistant approved articles-லிருந்து reply draft பண்ணுகிறது. Track செய்ய வேண்டியது API latency மட்டும் அல்ல: correct article retrieve ஆனதா, agent edit எவ்வளவு, unsupported claim வந்ததா, response time குறைந்ததா, customer reopen rate என்ன?

## Fix செய்வதற்கு முன் classify பண்ணுங்க

Failure system, retrieval/data, prompt/model, workflow/UX அல்லது policy/permission layer-ல் இருக்கிறதா identify பண்ணுங்க. Wrong layer fix செய்வது symptom hide பண்ணலாம்.

## Safe improvement loop

Observe → reproduce → classify → smallest change → offline test → controlled release → compare metrics → keep அல்லது rollback.

Prompt/model/config/version அனைத்தையும் record பண்ணுங்க. Multiple variables ஒரே நேரத்தில் change பண்ணினால் cause identify பண்ண முடியாது.

## Common mistakes

<Mistakes>

- Uptime மட்டும் measure செய்து user outcome ignore பண்ணுவது.
- Negative feedback வந்தவுடன் prompt random-ஆ change பண்ணுவது.
- Failed examples evaluation set-க்கு add பண்ணாமல் விடுவது.
- Users workaround செய்வதை adoption என்று report பண்ணுவது.
- Rollback threshold மற்றும் owner define செய்யாமல் release பண்ணுவது.

</Mistakes>

## Interview-ல் எப்படி explain பண்ணுவது?

<ThemeCard title="FDE deployment success-ஐ எப்படி measure பண்ணுவீங்க?" badge="CAREER">

System health, AI answer quality, workflow adoption மற்றும் agreed business outcome ஆகிய layers-ல் baseline/target define பண்ணுவேன். Failures classify செய்து smallest controlled change release பண்ணி before/after evidence compare செய்வேன்; threshold fail ஆனால் rollback பண்ணுவேன்.

</ThemeCard>

## நினைவில் வைக்க வேண்டிய key points

<Takeaways>

- Production usage assumptions-ஐ evidence-ஆக மாற்றும்.
- Technical health necessary; outcome success-க்கு sufficient இல்லை.
- Failure-ஐ correct layer-ல் classify பண்ண வேண்டும்.
- One controlled change cause/effect-ஐ clearer ஆக்கும்.
- Every release-க்கு observation மற்றும் rollback தேவை.

</Takeaways>
