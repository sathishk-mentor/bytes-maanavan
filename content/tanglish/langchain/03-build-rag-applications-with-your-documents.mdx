## Concept-ai Simple-a Purinjukonga

Idha oru library madhiri nenachukonga. 40-page document-ah full-a padikardhukku பதிலா, oru smart librarian irundha, "transaction limit"-pathi kekka, andha specific paragraph mattum eduthu tharuvaanga — book full-a padikkanum-nu venaam. **Retrieval** system, adhே librarian job pannudhu.

Process naalu steps:

1. **Load** — document-ah (PDF, text, webpage) system-ku kondu varuradhu.
2. **Split** — periya document-ah chinna chinna "chunks"-a pirikuradhu (library-la books, chapters-a pirikardhu madhiri).
3. **Embed** — ovvoru chunk-ku, oru "meaning fingerprint" (embedding vector) create pannuradhu — similar meaning content-ku similar fingerprint irukum.
4. **Store & Retrieve** — indha fingerprints-ah oru vector database-la store pannuradhu, user question vandha, adhே question-oda fingerprint-oda closest match irukura chunks-ah edukuradhu.

Rahul kekkuraan: "Embedding-nu solna exact-a enna?" Divya: "Oru numbers-oda list-nu nenachuko — 'transaction limit' and 'withdrawal cap' — vaarthai vேறு, aana meaning similar-a irukanum-la, adha capture panra numbers."

## Inside Workflow

**Text Splitters** — chunk size romba important. Chinna-a pannina (100 characters), context lose aagum. Periya-a pannina (5000 characters), irrelevant info-um sேருthu varum. Typical-a 500-1000 characters, konjam overlap (100 characters) vachi split pannuvom — context boundary-la information lose aagadhu.

**Vector Stores** — embeddings store panra database (Chroma, Pinecone, FAISS, pgvector). User query vandha, adhே query-um embed panni, **similarity search** (cosine similarity) use panni, closest matching chunks-ah rank pannitu return pannum — idha "top-k retrieval" nu solluvom (example: top 3 relevant chunks).

**Retriever** — LangChain-la idhu oru Runnable — query kudutha, relevant documents return pannum, next chain step-ku (usually model call) pogum.

## Code Panni Paapom

```python
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import StrOutputParser

# 1. Load - PDF document-ah load pannuradhu
loader = PyPDFLoader("paisawise_policy.pdf")
documents = loader.load()

# 2. Split - chunks-a pirikuradhu, overlap vachi
splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100)
chunks = splitter.split_documents(documents)

# 3. Embed + Store - vector database create pannuradhu
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Chroma.from_documents(chunks, embeddings)

# 4. Retrieve - relevant chunks edukuradhu (top 3)
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# 5. RAG chain - retrieval + generation combine pannuradhu
prompt = ChatPromptTemplate.from_template(
    "Answer using ONLY this context:\n{context}\n\nQuestion: {question}"
)
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

rag_chain = (
    {"context": retriever, "question": lambda x: x}
    | prompt
    | model
    | StrOutputParser()
)

answer = rag_chain.invoke("En transaction limit evlo?")
print(answer)
```

## Practical Cost Scenario

**Important:** Keela irukkura banking-scale numbers sample estimate mattum. HDFC-oda internal implementation or verified cost claim illa. Actual token cost provider pricing and document size-la depend aagum.

HDFC madhiri banking scale-la yosichaal, whole policy manual-ah ovvoru query-kum prompt-la kudutha — oru query-ku approximately **8,000-10,000 tokens** aagum (₹3-4 per query, GPT-4-class model rate-la). RAG approach use panna, relevant 3 chunks mattum (~1,200 tokens) kudukardhala, query cost **₹0.40-0.50**-ku வந்துடுச்சு — **~85% cost reduction**, and accuracy-um improve aagum (model irrelevant info-la confuse aagadhu).

PaisaWise-oda case-la, support team-oda "policy lookup" time, average **4 minutes** -la irundhu **8 seconds**-ku குறைஞ்சுடுச்சு — daily 200 queries-ku, andha saved time-ah agent-oda hourly cost-la convert pannina, **₹18,000/month** equivalent productivity gain.

## Common Mistakes

1. **Chunk size wrong-a set pannuradhu** — romba chinna-na context lose aagum, romba periya-na irrelevant noise varum.
2. **Overlap illama split pannuradhu** — important information oru sentence-oda naduvula chunk boundary vandha, adhே information rendu chunks-la split aagi, edhume complete-a retrieve aagadhu.
3. **Top-k value wrong** — k=1 na, sometimes correct answer miss aagum. k=10 na, irrelevant context-um sேருthu, model confuse aagum. Typically k=3-5 balanced-a irukum.
4. **Embedding model and query language mismatch** — Tanglish/Tamil queries-ku, embedding model adha well handle pannudha-nu check pannama use pannuradhu.
5. **"Answer using only this context" instruction miss pannuradhu** — idhu illama, model hallucinate pannalam (context-la illaadha info-ah confident-a sollalam).

## Key Takeaways

## FAQ + Knowledge Check

**Q1: RAG and fine-tuning-ku enna difference?**
RAG, external knowledge-ah runtime-la inject pannudhu (facts venumna). Fine-tuning, model-oda behavior/style-ah training mூலம் maathudhu. Frequently changing facts-ku RAG better.

**Q2: Vector database yaen venum, normal SQL database use pannalama?**
SQL database exact match/keyword search-ku nalla irukum. Vector database "meaning-based" (semantic) search panna design pannirukku — vாrthai different-a irundhalum, meaning similar-a irundha kandupidikum.

**Q3: Embedding model, chat model rendum same-aa?**
Illa, rendum vேறு purpose. Embedding model text-ah vectors-a convert pannudhu (search-ku). Chat model text generate pannudhu (answers-ku).
