## Concept-ai Simple-a Purinjukonga

Memory-ah oru "call center agent-oda notebook" madhiri nenachukonga. Nalla agent, customer call panna, previous conversation notes paathu, context-oda continue pannuvaanga. Bad agent, ovvoru thadavayum "Yenga peru enna, prachana enna"-nu முதலில் இருந்து கேக்குவாங்க — irritating experience.

LangChain-la memory, conversation history-ah store panni, ovvoru new call-oda kudukum — so model-ku "idhukku munnadi enna pesinom"-nu theriyum. Rendu main approaches:

1. **Full history** — ella messages-um store panni, ovvoru call-kum full history kudukuradhu. Simple, aana conversation neela neela, token cost increase aagum.
2. **Summarized/windowed memory** — recent N messages mattum vைthukonga, illa periya conversation-ah summary-a compress pannunga — token cost control-la vைthukonga.

Meena kekkuraanga: "Memory permanent-a irukuma, illa session mudinja poidumaa?" Divya: "Design choice dhaan — chat session mattum-ku (in-memory), illa database-la persist panni customer next login-la um continue pannalam."

## Inside Workflow

LCEL-based apps-la, memory usually **`RunnableWithMessageHistory`** wrapper use panni implement pannuvom. Idhu ovvoru session-ku (session_id use panni) separate history maintain pannum — so Customer A-oda conversation, Customer B-oda conversation-oda mix aagadhu.

**Message history storage options:**
- **In-memory** — simple, aana app restart aana lose aagum.
- **Database-backed** (Redis, PostgreSQL, MongoDB) — production apps-ku recommended — persist aagum, scale aagum.

**Trimming/Summarization strategies:**
- **Trim** — oldest messages-ah drop pannuradhu, recent N mattum vைthukoradhu.
- **Summarize** — periya history-ah, oru chinna summary-a compress pannuradhu (LLM use panni), so context lose aagama, token cost-um control-la irukum.

## Code Panni Paapom

```python
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_openai import ChatOpenAI

# Session-based storage - production-la Redis/DB use pannunga
store = {}

def get_session_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

prompt = ChatPromptTemplate.from_messages([
    ("system", "Neenga PaisaWise-oda finance assistant. Tanglish-la pesunga."),
    MessagesPlaceholder(variable_name="history"),
    ("human", "{input}")
])

model = ChatOpenAI(model="gpt-4o-mini", temperature=0.3)
chain = prompt | model

chain_with_memory = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="history"
)

config = {"configurable": {"session_id": "customer_12345"}}

# First question
r1 = chain_with_memory.invoke({"input": "En food expense evlo?"}, config=config)
print(r1.content)  # "Rs 4,500 daa indha maasam"

# Follow-up - "adhula" refers to previous answer, model-ku context therியும்
r2 = chain_with_memory.invoke({"input": "Adhula Swiggy evlo?"}, config=config)
print(r2.content)  # Correctly understands "adhula" = food expense breakdown
```

## Practical Cost Scenario

**Important:** Keela irukkura scale and CSAT numbers learning scenario mattum. Zomato/Eternal அல்லது PaisaWise verified internal metrics illa.

Zomato/Eternal-oda customer support chatbot madhiri scale-la nenachukonga — daily lakhs conversations, average 6-8 turns per conversation. Full history ovvoru turn-kum kudutha, token usage exponentially increase aagum — 8th turn-ku, first turn-oda 8 times tokens venum. Windowed memory (last 4 turns mattum) use panna, token cost **~60% குறையும்**, aana most conversations-ku context sufficient-a irukum (customers rarely 4 turns-ku appuram old topic refer pannuvaanga).

PaisaWise-oda case-la, memory add pannina apram, customer satisfaction score (CSAT) **3.2/5 to 4.4/5**-ku improve aachu — "bot ninaichukudhu" nu customers feel pannuraanga.

## Common Mistakes

1. **Session ID manage pannaama poradhu** — Customer A and Customer B-oda history mix aana, privacy issue-um confusion-um varum.
2. **Unlimited history growth** — token cost and latency, conversation neela neela unnecessary-a increase aagum.
3. **Memory-ah "permanent database"-nu confuse pannuradhu** — chat memory, structured data storage-ku substitute illa. Transaction records-ah database-la than store pannanum, chat history-la illa.
4. **Sensitive data memory-la store pannuradhu** — PAN number, OTP madhiri sensitive info, chat history-la unnecessary-a store panna kudathu.

## Compare Panni Decide Pannunga

| Approach | When to Use |
|---|---|
| No memory (stateless) | Single-turn Q&A, independent queries |
| Full history memory | Short conversations, accuracy > cost priority |
| Windowed/summarized memory | Long conversations, production scale, cost-sensitive |

## Key Takeaways

- Memory illama, ovvoru message standalone-a treat aagum — follow-up questions fail aagum.
- **`RunnableWithMessageHistory`** — session-based conversation history manage panna help pannum.
- Production apps-ku, database-backed storage (Redis/PostgreSQL) recommended — in-memory app restart-la lose aagum.
- **Windowing/summarization** — long conversations-la token cost control panna essential.
- Memory, structured data storage-ku substitute illa — sensitive info separate-a, properly store pannanum.

## FAQ + Knowledge Check

**Q1: Memory illama chatbot build panna mudiyumaa?**
Mudiyum, aana multi-turn conversations-la follow-up questions handle panna mudiyaadhu. Simple single-turn tools-ku memory venaam.

**Q2: Session ID enna vைchi generate pannuvom?**
Usually user_id, illa unique session token (login session, browser session) use panni generate pannuvom.

**Q3: Summarized memory-la, oru risk enna?**
Summarization-la, konjam detail lose aagalam — LLM summary generate pannumbodhu, edge-case details miss aagalam.
